# se-task-executor 参考

## 需人决策 vs 其他阻塞

| 情况                                     | 去向                                  | 本轮是否继续其他任务       |
| ---------------------------------------- | ------------------------------------- | -------------------------- |
| 架构/数据模型/API/核心流程改变           | `plan/`，改名为 `TASK-<编号>-plan.md` | 是                         |
| 可能与其他任务产生根本性冲突             | `plan/`，改名为 `TASK-<编号>-plan.md` | 是                         |
| 产品未决、需求冲突、范围不清、缺验收标准 | `plan/`，改名为 `TASK-<编号>-plan.md` | 是                         |
| 外部环境、密钥、第三方账号不具备         | `blocked/`，保留原文件名              | 是                         |
| 依赖的 TASK 仍在 `active/` 未完成        | 留在 `active/`，本轮跳过              | 是                         |
| 实现中验证失败、缺护栏、无法安全改代码   | 停这一条；能回退则回退                | 若还有别的可执行任务则继续 |
| 用户要求停止                             | 全部停止                              | 否                         |

## 文件名

- `active/`：`TASK-<三位或更多数字>-<短名>.md`
- `plan/`：`TASK-<同一编号>-plan.md`
- 编号从原文件名提取，不要新编。
- 正文标题（`# TASK-XXX: <任务名称>`）保持不变，便于人认出来。

## Decision Needed 写法

只写人必须拍板的问题，不要写实现步骤。

```markdown
## Decision Needed

- 未登录访问受保护页时：重定向到登录，还是展示 403？
- 是否允许邮箱+手机号同时作为登录标识？任务与 ADR-overview 未覆盖。
```

每条都应能用一句话回答。不要写「请确认需求」这类空话。

## 架构/数据模型/API/核心流程改变

下列任一即进入 `plan/`，即使任务看起来写得很完整：

- 新增或改动 ADR 所覆盖的分层、进程边界、协议（如 AG-UI / HTTP / IPC）
- 改表结构、实体关系、持久化字段语义、迁移策略
- 改公共 API 的路径、方法、请求/响应、错误码、鉴权
- 改主路径：登录、会话、消息投递、Agent 循环、部署/启动顺序等

内部函数拆分、文件搬家、局部实现细节不算。

## 与其他任务的根本性冲突

「根本性」指目标、数据模型、API 或核心流程互相否定，而不是实现顺序或依赖先后。

- 先扫 `active/`、`plan/`、`blocked/` 的 Goal / Scope / Requirements
- 两边不能同时为真 → `plan/`，在 `Decision Needed` 写明冲突的 TASK 编号和矛盾点
- 只是「要等 TASK-XXX 先做」→ 本轮跳过，不要进入 `plan/`

## 不要当成 plan/ 的情况

- 技术步骤未拆分：执行 Agent 自己决定内部步骤，不把这当作产品决策。
- 文件怎么命名、函数怎么拆：不是人决策。
- 测试怎么写：不是人决策，除非验收标准本身缺失。
- 依赖任务还没做完：跳过，不要移入 `plan/`。

## 明确执行 plan/ 任务时

仅当用户点名某条 `TASK-xxx-plan.md`（或等价表述）时：

1. 仍按 TASK 正文实现与验证。
2. 填写 Completion，`Status` 设为 `COMPLETED`。
3. **文件留在 `plan/`，不要归档。**
4. 提醒用户手动移到 `.ai/tasks/archive/<年份>/`。
